# Boidwip — working notes

Everything above this line is generated by `next dev`. Leave it alone; edit only

Read [README.md](README.md) first for what this project is and how it fits
together. This file is only the things that are easy to get wrong.

## The one architectural fact everything follows from

The public site is **fully static**. `lib/data.ts` reads Payload's Local API
during `next build`; visitors never touch Postgres. So:

- There is nothing to revalidate at request time. "Publish" means "rebuild",
  triggered by a Vercel Deploy Hook from Payload's `afterChange` / `afterDelete`
  hooks (`lib/payload/revalidate.ts`).
- Do not add `dynamic = "force-dynamic"`, request-time `fetch`, cookies or
  headers to anything under `app/(frontend)`. A single dynamic dependency turns a
  prerendered page into a serverless function.
- Route handlers are **dynamic by default** in Next 15+. Any new one under
  `app/(frontend)` that serves fixed content needs
  `export const dynamic = "force-static"`, or it silently becomes a function
  invocation behind a file that never changes. `rss.xml` and `ads.txt` both
  needed this.
- After changing anything in the data or routing layer, check the build's route
  table. Every public route should be `○` (prerendered) or `●` (SSG). Exactly
  four routes are legitimately `ƒ`, and no others:
  `/admin/[[...segments]]`, `/api/[...slug]`, `/api/cron/rebuild`, `/preview`.
  `/preview` is request-time on purpose (it reads the admin session cookie),
  which is why it lives in its own `app/(preview)` route group rather than as
  an exception inside `app/(frontend)`.
- **`buildStore()` loads the whole catalogue into memory, once per build worker,
  and that is the right shape here** — not a query-per-page one that a
  request-time architecture would want. What it must not load is the heavy
  columns: chapters are fetched with an explicit `select` that leaves the Lexical
  `body` in Postgres, because `depth: 0` does *not* drop it (depth controls
  relationships, `body` is a field on the chapter itself). Adding a field to that
  `select` list is how this turns back into an out-of-memory build.

## Payload config: two rules that fail confusingly

`payload.config.ts` is loaded by Payload's CLI through tsx, **outside** Next's
bundler. Therefore:

1. **Relative imports only** in the config and everything it reaches
   (`collections/*`, `lib/payload/*`, `lib/types.ts`). The
   `@/` alias resolves from tsconfig paths, which is not guaranteed there.
   `next build` compiles fine while every `payload` command dies on
   module-not-found — so this breaks the CLI, not the app, which is why it is
   easy to introduce without noticing.
2. **Register admin components by string path, never by import** —
   `"/components/payload/seo/SerpPreview#default"`, resolved from
   `admin.importMap.baseDir`. The CLI cannot compile a `.tsx` file or a CSS
   module. Run `npm run generate:importmap` and commit
   `app/(payload)/admin/importMap.js` after adding one.

## Schema changes

```bash
npm run payload migrate:create   # writes migrations/*.ts
npm run payload migrate          # applies locally
npm run generate:types           # regenerates payload-types.ts
```

Commit the migration. `npm run build` runs `payload migrate` first.

`payload-types.ts` and `app/(payload)/admin/importMap.js` are **generated files
that are committed**, and CI fails if either is stale (see the checks section
below). Regenerate them in the same commit as the change that invalidates them:
`npm run generate:types` after any field change, `npm run generate:importmap`
after registering an admin component by string path.

Drizzle `push` is off in **every** environment, development included. It is not a
convenience that was forgotten — it drifts the schema without producing a
migration file, so everything works locally and production deploys with nothing
to apply. Never turn it on to "just make it work".

Postgres gives collections **numeric** ids. Anything crossing an HTTP boundary
(a `<select>` value, a query param) arrives as a string and must be coerced.

## The matched pair that fails silently

`lib/payload/editor.ts` (what the Lexical editor can produce) and
`sanitizeContentHtml()` in `lib/render.ts` (what survives to the page) must be
kept in step. A feature enabled in one and missing from the other produces **no
error anywhere**: the editor shows the content, the published page does not.
Change both in the same commit, and never loosen the allowlist just to make
something appear without understanding why it vanished.

Likewise `RIGHTS_TIERS` and `RESERVED_ROUTE_SLUGS` in `lib/types.ts` are single
sources of truth — `collections/Books.ts` builds its tier select options from
the former, and `collections/Pages.ts` validates slugs against the latter.
Don't retype either list.

## Three more things that fail silently, all in the frontend

**Metadata file conventions are not all detected in a route group.**
`sitemap.ts`, `robots.ts`, `opengraph-image.tsx` and `manifest.ts` are Next file
conventions, but they do not agree about where they may live. `sitemap.ts` and
`opengraph-image.tsx` work inside `app/(frontend)`; `manifest.ts` is **only**
picked up at the app root. With an identical file inside the route group the
build emitted no `/manifest.webmanifest` route and no `<link rel="manifest">` at
all, with no warning. Hence `app/manifest.ts` and `app/robots.ts` sit at the
root while the rest of the public metadata lives in the group. If you add a new
metadata convention file, confirm it in the build's route table before believing
it works.

Related: the `manifest:` field in `app/(frontend)/layout.tsx`'s `metadata` is
deliberately absent. The file convention already emits the link tag; setting
both produces two identical tags.

**The 404 is `app/global-not-found.tsx`, and `not-found.tsx` cannot do its job
here.** Same family of trap as the paragraph above, and it shipped broken. There
is no `app/layout.tsx`: `(frontend)`, `(payload)` and `(preview)` each render
their own `<html>`, so this app has **three root layouts**. Next resolves the
global 404 — the one an unmatched URL gets — at the app root and needs a root
layout to render it inside, and an unmatched URL belongs to no group, so there is
nothing to compose one from. `app/(frontend)/not-found.tsx` was therefore reached
only by an explicit `notFound()` from inside that group, and everything else fell
through to Next's built-in default: 7 KB of English "This page could not be
found" on a bare `<html>` with no `lang`, no stylesheet and no navigation.

`global-not-found.tsx` is Next's own answer to this (its docs name "multiple root
layouts" as the reason it exists). Three consequences:

- It **skips every layout**, so it must return a complete document and import
  `globals.css`, the font and the theme script itself. Those last two now live in
  `lib/fonts.ts` and `lib/themeScript.ts` so the layout and the 404 share one
  instance — a second `Noto_Sans_Bengali()` call would mint a second class name,
  and `--font-body` would be scoped to a class the 404's `<html>` never carries,
  so that page alone would render in the system Bengali font.
- It is gated on `experimental.globalNotFound` in `next.config.mjs`. **Treat that
  flag as load-bearing**: without it the file is ignored and the default 404
  returns, with no warning. `next build` prints `✓ globalNotFound` under
  "Experiments" when it is on.
- The body markup is `components/NotFoundContent.tsx`, shared with the in-group
  `not-found.tsx`, because the two shells must differ and the page must not.

Why the gap was near-total rather than an edge case: every dynamic route sets
`dynamicParams = false`, so a param `generateStaticParams` did not return is
refused by the router without ever running the page component. A mistyped or
stale link — the most likely 404 on a site whose URLs get shared between
readers — never reached the `notFound()` in `book/[slug]/read/[chapter]/page.tsx`.

Check it the way it was caught, since none of this surfaces as an error: grep the
built file, don't trust the route table. `.next/server/app/_not-found.html` should
contain `৪০৪` and no `This page could not be found`, and
`_not-found.meta` should say `"status": 404`.

**Colours go through the design tokens in `tailwind.config.ts`, never raw
Tailwind palette classes.** Tokens are defined as
`token = (name) => \`rgb(var(${name}) / <alpha-value>)\`` rather than a plain
`var(--x)`, because a plain var compiles but silently drops the alpha channel, so
`bg-surface/50` renders fully opaque. Both themes are one set of variables, which
is why almost nothing in `app/` or `components/` needs a `dark:` variant. The
exceptions are on purpose: ThemeToggle's icon swap and the amber preview banner.

The reason to care: **Tailwind emits nothing for a colour class it does not
recognise, and does not warn.** `text-ink` after `ink` was removed from the
config is not an error, it is invisible black-on-black in one theme only.

## Reviews: a first-party public write on a static site

Reviews are the one place readers write to the database, and they had to fit
the static model without breaking it. Three facts follow:

- **The list is fetched in the browser, not baked at build.** `components/ReviewSection.tsx`
  does a lazy `GET /api/reviews?…` on scroll. If it were
  server-rendered, a moderator approving a review would need a full rebuild, and
  every page render would hit Postgres. So the page HTML stays static; an approval
  shows up on the next page view. There is deliberately **no rebuild hook** on
  the Reviews collection for this reason.
- **The collection is the wall; the endpoint is the only door.** `Reviews.access.create`
  is `() => false`, so the generic `POST /api/reviews` is closed to everyone.
  Every public review arrives through `lib/payload/submitReview.ts`
  (`POST /api/reviews/submit`, mounted on the collection so it inherits the
  already-dynamic `/api/[...slug]` — no new `ƒ` route), which length-checks,
  resolves the book (published only), verifies Turnstile, rate-limits by
  salted IP hash, and forces `status: "pending"` before `payload.create` with
  `overrideAccess`. Anonymous reads are filtered to `status: approved`, and
  `authorEmail` / `ipHash` are hidden by field-level access.
- **Turnstile degrades like every other optional integration.** `lib/turnstile.ts`
  (server) and `components/Turnstile.tsx` (client) key off the paired
  `TURNSTILE_SECRET_KEY` / `NEXT_PUBLIC_TURNSTILE_SITE_KEY`. Unset → the widget
  renders nothing and the server skips the check; the moderation queue is the
  backstop. It also **fails open on a Cloudflare network error** but closed on an
  explicitly invalid token. Turnstile's script and iframe hosts
  (`https://challenges.cloudflare.com`) are in the CSP `script-src`/`frame-src`/
  `connect-src` in `next.config.mjs` — a review-widget host that is missing
  there is blocked with no error on the page, only in the console.

## Turnstile on the admin login

A **separate** Turnstile key pair from the review widget
(`NEXT_PUBLIC_TURNSTILE_LOGIN_SITE_KEY` + `TURNSTILE_LOGIN_SECRET_KEY`, each
falling back to the review pair when unset). They are separate because one
Turnstile site key carries a single dashboard-chosen widget mode: the review
key is invisible, the login key is a visible Managed checkbox, and one key
cannot be both. The login also could not reuse the review *approach*: Payload
ships its own `<LoginForm>`, it posts only `{email, password}`, and there is no
supported seam to add a token to that submission. Replacing the whole login view
to inject one is the version-coupled fragility this file warns against
everywhere else. So the check is decoupled from the form with a one-time gate
cookie, in `lib/payload/loginTurnstile.ts`:

- `components/payload/auth/LoginTurnstile.tsx` renders the widget in Payload's
  `beforeLogin` slot (`admin.components.beforeLogin` in `payload.config.ts`),
  visible (`appearance: "always"`) rather than invisible, using the login site
  key. On a passed challenge it POSTs the token to `turnstileGateEndpoint`
  (`POST /api/users/turnstile-gate`, mounted on Users so it adds no `ƒ` route).
- The endpoint verifies the token with Cloudflare **server-side** (via
  `verifyLoginTurnstile`, which uses the login secret and fails closed) and only
  then sets a short-lived (5 min) httpOnly cookie signed with `PAYLOAD_SECRET`.
- `enforceTurnstileGate` runs as a `beforeOperation` hook on Users for
  `operation === "login"` — **before the password is checked** — and rejects the
  login unless that cookie verifies. A script POSTing straight to
  `/api/users/login` never passed the widget, so it has no valid cookie.

**The lockout guard is the load-bearing detail.** The gate is enforced only when
`isLoginTurnstileConfigured()` is true, which requires BOTH the login secret AND
the login public key. Gating on the secret alone was the original bug: with the
secret set but no public key (or a key whose widget can't render), the hook
demanded a cookie the widget could never mint, and the login screen showed
"complete the verification challenge" with no challenge on it — a hard lockout.
Requiring both means a half-configuration disables the gate instead of bricking
login. It still fails **closed** on a Cloudflare outage once both are set (an
admin login is not a moderated queue); the escape hatch then is to unset
`TURNSTILE_LOGIN_SECRET_KEY` (and `TURNSTILE_SECRET_KEY`), which disables the
gate with no code redeploy. With neither pair set the stock login is unchanged.

**Configuration presence is not challenge availability, and that gap was the
second lockout.** `isLoginTurnstileConfigured()` proves two environment variables
exist; it says nothing about whether a challenge reached the screen.
`turnstile.render()` returns a widget id and creates the hidden
`cf-turnstile-response` input *before* the iframe arrives, and when the iframe
never arrives — this host missing from the sitekey's Cloudflare "Domains" list, a
blocked cross-origin frame, an extension, or Cloudflare's own error 300030
("Turnstile Widget seem to have hung") — **every callback stays silent and the
container stays zero-height**. Seen live during testing: `iframeCount: 0`,
console `Error: 300030`, and the login screen refusing every attempt next to an
empty gap.

There is no error event for that case, so `components/Turnstile.tsx` reports it
on a timer: `RENDER_TIMEOUT_MS` (10s), then a check for an `iframe` inside its own
container, feeding a new `onError(reason)` prop — deliberately separate from
`onVerify(null)`, because an expired token means "ask again" and this means
"asking again will not help". It fires at most once per mount, and is skipped for
`appearance: "execute"`, where an absent iframe is the expected state.
`components/payload/auth/LoginTurnstile.tsx` turns that into visible copy naming
the likely causes and the unset-the-secret escape hatch; the public review form
passes no handler, because an unprotected review still lands in the moderation
queue.

**That path reports, it never unlocks.** The server gate stays enforced whatever
the browser claims, since "the widget broke" is a one-line forgery that would
otherwise become a universal bypass. The fix for a real hang is an environment
change by the administrator, which is why the message on the login screen names
the variable to clear.

Not done, on purpose: **forgot-password is not Turnstile-gated.** Payload gives
the ForgotPassword view no `beforeLogin`-style slot, so the widget can't be shown
there without overriding the whole view, and gating the operation without a
visible challenge would just break it. What that operation *is* guarded by is the
email check below.

## Forgot-password mail, and the success that isn't one

`lib/payload/email.ts` is the whole feature: it resolves an SMTP transport from
the environment and hands it to `@payloadcms/email-nodemailer`, and it registers
`enforceEmailDelivery` as a `beforeOperation` hook on Users for
`operation === "forgotPassword"`.

**The reason it needs a guard at all is a silent success.** With no `email:` in
the config Payload does not fail — it falls back to `consoleEmailAdapter`, which
logs `Email attempted without being configured` and **resolves successfully**. So
the reset screen printed its confirmation, the operation returned 200, a
`resetPasswordToken` was written to the user row, and the only copy of the link
went to a server log. A locked-out admin waits for mail that was never sent. The
hook refuses the operation instead, before the user lookup and before any token
is minted, with an `isPublic` message that names the fix.

**Three providers: `SMTP_*` beats `BREVO_*` beats `GMAIL_*`.** Most specific
intent wins — someone who typed a host name knows which server they mean. Gmail
(`GMAIL_USER` + `GMAIL_APP_PASSWORD`) is the zero-setup option; Brevo
(`BREVO_SMTP_USER` + `BREVO_SMTP_KEY` + `EMAIL_FROM_ADDRESS`) is the upgrade for
volume; the generic pair (`SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` /
`SMTP_PASSWORD` / `SMTP_SECURE` + `EMAIL_FROM_ADDRESS`) is anything else speaking
SMTP. Any two may be set at once, which is the point: a migration is adding
variables rather than swapping them atomically and hoping.

**Why the generic branch exists, because the Gmail branch looks like it already
covers "an address I own".** It does not, and the failure actively misleads.
`GMAIL_*` hardcodes `host: "smtp.gmail.com"`, and Gmail's SMTP authenticates
against a **Google account** — so `GMAIL_USER` must be `@gmail.com` or a Google
Workspace address on a domain Google hosts. Point it at a mailbox from a
registrar, cPanel, Zoho or Hostinger and Google answers `535-5.7.8 Username and
Password not accepted ... BadCredentials`, which reads exactly like a wrong App
Password and sends people to regenerate a credential that was never the problem.
The credential was right; the SERVER was wrong. `warnIfSuspectGmailUser` names
that case at boot instead of leaving it to the 535, and it warns rather than
refusing, because a Workspace domain is indistinguishable from any other domain
from inside the process.

Four details that are each a silent failure if got wrong:

- **`EMAIL_FROM_ADDRESS` is required for `SMTP_*` and Brevo, ignored by Gmail.**
  Neither of the first two has a mailbox to infer (`SMTP_USER` is often an
  identifier, as with Mailgun or SES; Brevo issues `…@smtp-brevo.com`), so
  guessing would produce a 550 visible only in the log. Missing it makes that
  block count as unconfigured and fall through, rather than becoming a silently
  broken upgrade.

- **Gmail always sends as `GMAIL_USER`** and ignores `EMAIL_FROM_ADDRESS`. Gmail
  rejects a From the account does not own with a 553, so honouring an override
  there would break sending for anyone who set that variable early.
- **Brevo's SMTP login is not a mailbox** (it looks like
  `9a1b2c001@smtp-brevo.com`), so there is no address to infer there either, and
  the one you set must be a sender Brevo has verified.
- **The TLS mode is derived from the port, not defaulted.** `SMTP_SECURE`
  overrides, but by default 465 means implicit TLS and anything else means
  STARTTLS, made mandatory with `requireTLS` so a server that declines the
  upgrade fails instead of sending the password in clear. Getting the
  port/secure pair wrong hangs the handshake rather than erroring, which is a
  much worse thing to debug than a rejection.
- **App Passwords are pasted with spaces.** Google displays them as four groups
  of four; SMTP AUTH does not ignore the spaces, and the failure reads as a wrong
  password. Both it and `SMTP_PASSWORD` are whitespace-stripped, for the same
  reason: provider dashboards render long keys in groups and people paste what
  they see.

**`nodemailerAdapter()` must never be reached unconfigured.** Called with no
`transport`/`transportOptions` it creates an **ethereal.email test account over
the network** and console-logs its credentials — mail then goes to a fake inbox
and every send reports success. That is why `emailAdapter()` returns `undefined`
without importing the package, rather than a ternary that calls the adapter with
partial args. `Config.email` accepts `EmailAdapter | Promise<EmailAdapter>`, so
the async adapter is passed unawaited and the config stays synchronous.

`skipVerify` is on in production only. The adapter's boot-time
`transport.verify()` authenticates against the SMTP server, which is what surfaces
a wrong App Password immediately in development; in production it is a handshake
per cold start that buys nothing, because the adapter only `console.error`s the
result and sends anyway.

The mail's **subject** is overridden in `collections/Users.ts` (a bare "Reset your
password" from a personal Gmail address reads as phishing); its **body is
deliberately Payload's**, because overriding it means rebuilding the reset URL out
of serverURL + admin route + reset route + token, and getting any part wrong ships
a well-branded email with a dead link.

## Rebuild hooks

**These hooks trigger deployments. They do not invalidate caches — there is no
cache to invalidate.** The file used to describe itself as tag-based
revalidation: `'use cache'` + `cacheTag()` in the data layer, `revalidateTag()`
here. Every sentence of that was aspirational. `cacheComponents` is not enabled
in `next.config.mjs`, so `'use cache'` and `cacheTag()` are not available and
`lib/data.ts` contains neither — there was no cache entry anywhere in the
project carrying any of the fourteen tags this module invalidated. And it could
not have worked even if there had been: every route pairs
`generateStaticParams()` with `dynamicParams = false`, so a slug that did not
exist at build time is a 404 whatever a cache is told. A newly published book
could not appear at all. The fan-out was elaborate, carefully commented, and
inert.

Four shapes, in `lib/payload/revalidate.ts`, and the distinction is
load-bearing:

- `rebuildOnPublish` — collections with drafts (Books, BookChapters, BlogPosts,
  Pages, Lists). Fires when a document crosses the published boundary or when an
  already-live one is edited, so draft→draft saves cost nothing. Also skips a
  book whose `publishDate` is in the future: `lib/data.ts` would filter it out
  anyway, so building now produces a byte-identical site, and the daily cron
  brings it live on the day.
- `rebuildAlways` — draft-less structural collections (Authors, Publishers,
  Categories, Series). No `_status` exists on them, so a publish-boundary check
  would silently never fire, and their fields appear on many pages.
- `rebuildOnDelete` — everywhere, and **undebounced** (`forceRebuild`), because
  a takedown is the one case where waiting up to 90 seconds is the wrong answer.
  It returns early for a draft that was never published: there was no page.
- `rebuildOnGlobalChange` — SiteSettings and AffiliateSettings. Every field on
  both renders on every page (footer, disclosure line, homepage rails), so a
  change is site-wide by definition and there is no narrower trigger to make.

`queueRebuild()` POSTs `VERCEL_DEPLOY_HOOK_URL` at most once per 90 seconds. The
claim is atomic and lives in Postgres (`lib/payload/kv.ts`), not in a
module-level variable: one editor action fires several hooks, and on Vercel two
concurrent saves land on two instances that share no memory.

**Nothing in this file throws.** The content is already committed by the time an
`afterChange` hook runs, so a deploy hook that is unreachable must not make a
save look like it failed. Failures record a dirty marker instead, and
`/api/cron/rebuild` sweeps it up daily. The hook URL is a credential — anyone
holding it can trigger unlimited production builds — so **no code path logs it**,
only status codes. Keep it that way.

The opt-out is still spelled `context: { skipRevalidate: true }` even though
nothing revalidates any more, because `content-seed/seed.mts` passes it on every
one of its ~40 writes; renaming it would silently make one seed run trigger
forty deployments.

## Renaming a slug moves a URL, and the redirect is a build artefact too

`lib/payload/slugHistory.ts` records `{from, to}` pairs in `payload_kv` on every
save (before the publish-boundary check, because a slug can be corrected while
still a draft), and `next.config.mjs`'s `redirects()` reads them back **once per
build** with `pg` directly. Read that function's header before touching either
end. Three consequences that are not obvious from either file alone:

- **A stored `source` is compiled as a path-to-regexp pattern, not a literal.**
  A value containing `:`, `*`, `(` or `?` would either match far more than the
  one URL it is meant to move or throw in `checkCustomRoutes` and fail the build,
  so anything that is not exactly `/`-separated `[a-z0-9-]` segments is dropped.
- **Redirects are matched before the filesystem.** A redirect whose old slug has
  since been taken back into use would shadow that live page, which is why
  `slugHistory.ts` deletes the row when that happens.
- **It fails open, on purpose.** A build machine with no reachable database still
  builds — the cost being a deployment whose old URLs 404 again rather than a
  failed deployment, so the warning it prints matters.

## Access control

Every collection sets `access` explicitly. When adding a collection, write its
`access` block at the same time as its fields, not afterwards — Payload mounts a
full REST API for it at `/api/<slug>` the moment it is registered, so a
permissive default is a live hole, not a theoretical one. Books, BookChapters,
BlogPosts, Lists and Pages restrict unauthenticated reads to
`_status: published` specifically so drafts can't be enumerated over HTTP.

GraphQL is disabled in `payload.config.ts` and its two route files were deleted.
Nothing here queries it (the build uses the Local API, the admin uses REST), so
it was capability-free attack surface: an endpoint whose purpose is to accept
arbitrary nested queries, on a site whose whole cost model is "no database
traffic at request time". Don't re-enable it without also setting a
`maxComplexity`. `maxDepth` is capped at 2 for the same reason — `?depth=10`
across mutually-referencing documents turns one cheap request into hundreds of
reads.

**Collection-level `read` is not enough for the rights block.** A published book
is publicly readable, so every field on it was public too — including
`rightsEvidence`, which holds a rights holder's name, their email address, the
text of their private email and the signed permission document. `GET
/api/books?depth=1` served all of it. Those fields now carry
`access: { read: authenticatedFieldRead }` individually (`collections/Books.ts`,
sidebar block), which is the only layer that can express "this document is
public, these fields are not".

**And a field rule cannot protect bytes on a public bucket.** `media` sets
`disablePayloadAccessControl: true` in `payload.config.ts`, which means the
stored URL *is* the R2 object's public URL and requests for it never reach
Payload at all — right for a book cover, catastrophic for a permission letter,
which would be public from the moment the upload finished and stay public after
the book was deleted. So evidence uploads go to `evidence-files`: a separate
collection, on a separate private bucket, with `disablePayloadAccessControl`
deliberately absent, so Payload serves the file from
`/api/evidence-files/file/<name>` and runs `read: authenticated` before streaming
a byte. Bind a public hostname to that bucket and the control is gone. Its
`beforeValidate` hook refuses uploads in production when `R2_EVIDENCE_BUCKET` is
unset, because the fallback is Vercel's ephemeral disk — a letter the compliance
record says exists and nobody can produce. **Objects already uploaded to the
public media bucket stay public**; that cleanup is the R2 audit step in
SECURITY.md and it is not done by code.

## The admin UI, and the five ways it breaks quietly

The admin is restyled by six unlayered stylesheets imported in
`app/(payload)/layout.tsx`. Read the header of `app/(payload)/theme/tokens.css`
before touching any of them. The mechanism, because it looks like magic
otherwise: Payload ships every rule inside `@layer payload-default`, and
unlayered CSS beats layered CSS **at any specificity**, so a one-line selector
here outranks Payload's three nested classes. Nothing needs `!important`, and
adding one is a sign the selector is wrong.

Against Payload they always win; against **each other** the ordinary cascade
applies, so the import order in `layout.tsx` is load-bearing and goes general to
specific:

| file | owns |
| --- | --- |
| `tokens.css` | the `--bdw-*` variables, both themes, and `prefers-reduced-motion` |
| `chrome.css` | the shell: nav, app header, doc toolbar, table, pills, dialogs, login |
| `surfaces.css` | which regions are canvas and which are paper |
| `fields.css` | form controls |
| `views.css` | page-level furniture: list toolbar, pagination, editor rail, versions, not-found |
| `responsive.css` | breakpoints, last, because a media query does not outrank a plain rule of equal specificity |

`surfaces.css` sits after `chrome.css` because both set `.nav`. `views.css` sits
after both because it re-fills `.list-controls`, which `chrome.css` gives a
margin, and it reads the `--bdw-canvas` that `surfaces.css` declares.

Every selector in these files was checked to exist in
`node_modules/@payloadcms/{ui,next}/dist/**/styles.css` before being written. A
class name that does not exist there produces no error, no warning and no style,
which is the same failure mode described above for Tailwind colour tokens. Check
before you add, not after it fails to appear.

A class existing is not the same as a selector matching, and the second one is
harder to catch. The document tab row was styled through `.doc-tab a`: `.doc-tab`
is real, `a` is a real element, and the whole block styled nothing, because a tab
has no anchor *inside* it. The clickable tabs **are** the anchors and the current
one is a `<div>` that Payload marks `.btn--disabled` so it cannot be clicked back
to. Verify against the rendered DOM, not against the class list: the symptom of
getting this wrong is a screen that looks like stock Payload while your stylesheet
appears to cover it.

That row is also the clearest example of the other half of the contract. Most of
Payload's interactive furniture is a `.btn` variant, and `.btn` reads
`--bg-color`, `--hover-bg`, `--color`, `--hover-color`, `--btn-border` and
`--btn-font-weight` for its own properties. Setting those variables is how
`fields.css` restyles every button without restating padding, radius or focus
rings, and it is how the tabs get theirs. Two traps in doing it: a variable set on
`.btn` in `fields.css` beats one set on a more specific Payload selector, because
unlayered wins and equal-specificity ties go to the later file (which is why the
active tab's weight is on `.doc-tab__label`, not on `--btn-font-weight`); and a
value Payload picks may be invisible rather than absent, as with the active tab's
`--theme-elevation-100` fill, which is exactly the canvas colour.

1. **Colours come from `--bdw-*`, never a hex.** Both admin themes are one set of
   variables in `tokens.css`, which is why almost nothing in `components/payload`
   needs a `[data-theme]` selector. A hardcoded hex is one theme's value applied
   to both, and it looks correct in whichever theme it was written in.
2. **A spinner alone is not progress.** The `prefers-reduced-motion` block in
   `tokens.css` sets `animation-iteration-count: 1 !important`, which freezes a
   spinner into a static ring rather than hiding it. Anywhere something is
   pending, say so in text too.
3. **`window.confirm` and `window.alert` are banned outright.** Use
   `useConfirm()` from `components/payload/modals/ConfirmContext.ts`; it resolves
   to a boolean, so the call site reads the same. `ConfirmProvider` is registered
   in `admin.components.providers`, which puts it *inside* Payload's
   `RootProvider` — that is what lets the dialog reuse Payload's modal container
   and its translated Cancel/Confirm strings instead of duplicating both.
4. **A button inside an admin form needs `type="button"`.** A typeless
   button submits the enclosing form. Every custom button under
   `components/payload` states its type for that reason.
5. **`--bdw-surface-raised` is not a card fill.** `surfaces.css` tints the canvas
   (`--bdw-canvas` is `--color-base-100`), and `--bdw-surface-raised` is
   `--theme-elevation-50`: `rgb(239,242,247)` against `rgb(247,248,251)` in the
   light theme, eight points apart on one channel. A panel sitting on the canvas
   and filled with `raised` does not read as a card, it reads as a rectangle with
   a border round it, and that alone is most of what makes a screen look flat.
   The pairing that works is `--bdw-surface` plus a shadow. `raised` is correct
   only for a panel nested **inside** a surface, which is where `.table thead`
   still uses it, and `--bdw-surface-sunken` is the right token for a tile
   inside a white block. There is no error either way, so this is a thing to
   check by eye against the canvas, not to assume.

   The corollary: `sunken` is `--theme-elevation-100`, the **same** colour as
   the tinted canvas. A sunken tile on paper is a compartment; the identical
   tile on the canvas is an empty border. So a panel whose children are sunken
   has to be a card itself, or their fills do nothing.

One layout rule that is not CSS, and it cuts both ways: **a view registered as a
named override must not render Payload's `<DefaultTemplate>`, and a view
registered with a `path` must.** Payload picks the template from the route it
matched, so a named-override route has already wrapped the override before it
renders and a second one nests a whole second sidebar and app header inside the
first (the symptom is a doubled sidebar on that view only). A view added at a new
path gets no template at all and has to supply its own.

Sizing against `--base`: Payload defines it as
`calc((var(--base-px) / var(--base-body-size)) * 1rem)` with `--base-px: 20` and
`--base-body-size: 13`, and its root font-size is 13px on desktop. So `--base` is
exactly 20px there, and 18.5px at 1024px and below where the root drops to 12px.
Worth knowing before sizing anything against a fixed-px icon.

## Checks, and the four ways a green suite lies

```bash
npm run typecheck    # tsc --noEmit — tests are typechecked too
npm run lint         # eslint .  — `next lint` was REMOVED in Next 16
npm test             # vitest: rights tiers, seo helpers, search, affiliate links
npm run build        # payload migrate && next build
npm run test:e2e     # playwright, against that build
```

**`npm run test:e2e` deliberately does not build**, and running it after `next
dev` is the mistake to avoid. `playwright.config.ts` starts `next start`, which
needs a build to already exist, because half of what these specs assert — the
prerendered HTML, the sitemap, canonical tags, whether a route really was
statically generated — does not exist under `next dev`. Dev would pass a suite
that a deploy then fails. First run also needs `npx playwright install chromium`.

**Both Playwright projects matter.** `chromium` runs the API and SEO specs;
`mobile` (Pixel 7) runs `*.mobile.spec.ts`, because the navigation drawer is
`lg:hidden` and those specs assert nothing on a desktop viewport. Two env vars
change what the suite does: `E2E_BASE_URL` tests a deployed URL instead of
starting a server (writes then default to off, so the review-submission spec
skips), and `E2E_ALLOW_WRITES=1` re-enables that one spec — only ever against a
database whose moderation queue you are willing to dirty.

**A build against an empty database produces an empty site.** The e2e specs are
data-driven and skip when there is nothing to inspect, so an unseeded run reports
a screen of green skips having asserted nothing at all. `npm run seed` is the
fixture; `.github/workflows/ci.yml` therefore spells out migrate → seed → build →
serve → test rather than calling `npm run build`, which would migrate *before*
the seed exists.

**The generated-file drift gate needs `.gitattributes` to be honest.** CI
regenerates `payload-types.ts` and the admin import map and runs `git diff
--exit-code` against what is committed — a stale `payload-types.ts` otherwise
lets code reading a long-deleted field keep typechecking for ever. This tree is
developed on Windows and is CRLF; a Linux runner writes LF, so without
`* text=auto` normalisation every line of a regenerated file differs and that
check is red on every run for a reason unrelated to the code. Both generators
load the config and open no connection, which is why the CI step passes a
syntactically valid `DATABASE_URL` pointing at nothing.

Dependency updates arrive as grouped Dependabot PRs (`.github/dependabot.yml`).
The `payload` group is grouped for a hard reason: `payload` and every
`@payloadcms/*` package are pinned to one exact version, and a tree holding two
of them at different versions typically fails at runtime rather than at install.
`.github/workflows/audit.yml` runs `npm audit --audit-level=high` weekly and
installs nothing, so it cannot execute a compromised install script while looking
for one.

## Conventions

- **Port 3000 locally, always.** Payload derives `serverURL`, `csrf` and `cors`
  from `NEXT_PUBLIC_SITE_URL`, falling back to `http://localhost:3000`. On
  another port, admin logins are rejected as cross-origin.
- **No em-dashes in public-facing strings**, in components or content. Code
  comments and these docs are exempt.
- **Admin chrome is English; the books' own vocabulary stays Bengali.** The
  labels, buttons, hints and headings an editor reads are English. Bengali is
  kept where an English translation would be the wrong word rather than a
  friendlier one: book titles, author names, category names, the rights-tier
  labels in `lib/types.ts`, stored field values, and everything on the public
  site. If you are adding a string, ask which of those two lists it belongs to
  before picking a language.
- **Field documentation goes in `admin.description`** on the field, not in a
  separate document. The editor reads it where the decision is being made.
- **Comment the *why*, not the *what*.** The existing comments in this codebase
  explain what would break if the code were written the obvious way; match that.
- App routes win the `/<slug>` space over Pages. `collections/Pages.ts` refuses
  a slug on the `RESERVED_ROUTE_SLUGS` list at save time — keep it that way.

## The logo lives in four places, and one of them is not SVG

The book-island mark is one design with four renderings, and changing it means
changing all four in the same commit:

| where | what it is |
| --- | --- |
| `components/SiteMark.tsx` | inline SVG, the public site's header |
| `public/icon.svg` | the favicon, referenced by `app/(frontend)/layout.tsx`, `app/manifest.ts` **and** `admin.meta.icons` in `payload.config.ts` |
| `components/payload/branding/{Logo,Icon}.tsx` | the admin's login mark and its collapsed nav mark, registered by string path |
| `app/(frontend)/og.png/route.tsx` | the same mark **rebuilt out of positioned `<div>`s** |

The last one is the trap. Satori, which `next/og` uses, does not render an inline
`<svg>` — it needs a real SVG file over HTTP, and an OG card must not depend on a
network fetch of its own origin at build time. So the mark there is `icon.svg`'s
64-unit geometry multiplied by 116/64 and expressed as absolutely positioned
divs. It cannot be regenerated from the SVG automatically, and nothing warns when
it drifts: the site's header and its social card simply stop showing the same
logo.

`defaultOGImageType: "off"` in `payload.config.ts` is deliberate. Payload's
per-page OG generator is on by default and mounts `/api/og` to render one at
request time, and every admin URL is behind a login, so each render would be for
a crawler that cannot reach the page.
